### V5.1 万吨级训练发散诊断 + ValueNorm 修复（2026-08-13，P1 第16条）

**发散现象**：正式基线训练（10kt_1plus0 万吨级 + 长大下坡，lr=5e-5）Reward 快速发散：
| 回合 | Reward | 超限次数 |
|:--|:--|:--|
| Ep 10 | -2691 | 1598 |
| Ep 20 | -3275 | 145718 |

调 lr=5e-6 无效 → 判定为算法层 bug 而非超参问题。

**根因诊断（两层）**：
1. **`log_prob` 未归一化**（已修复，V5.1 前）：`select_actions` / `update` 中 `log_prob` 直接求和，未按 `num_agents` 归一化（而 `entropy` 已归一化=铁证）→ 总 log_prob 被放大 ~101 倍 → 重要性采样 ratio 指数爆炸 → KL 早停 + 发散。修复：`total_log_prob += log_prob / num_drones`。
2. **value 目标尺度爆炸**（本次核心）：|returns| 可达 1e4~1e5，value 网络初始输出 ~0 → `value_loss ~1e8` → 硬编码 `total_loss>1000` 阈值**整回合跳过更新** → value 网络完全不训练 → 梯度被 clip 吞没、策略更新失真。
   - 证据：小编组验证时每回合触发 `Loss异常 >1000 跳过更新`（loss=0）。

**修复方案：ValueNorm（PopArt 简化版）**（`src/algorithms/mappo_agent.py`）：
- 新增 `ValueNorm` 类：running mean/std（Welford 增量更新）
- value 网络拟合**归一化 returns**（O(1) 尺度），`get_value` 推理时 `denormalize` 还原为真实回报尺度，保证与 GAE 中 rewards 同量纲
- 移除 `total_loss>1000` 硬编码阈值，改为 `torch.isfinite` NaN 检查
- checkpoint 保存/加载 `value_norm` 统计量（推理反归一化依赖它）

**修复后验证**：
- ✅ 4 个既有 mappo 测试通过 + 新增 2 个回归测试（大回报尺度不跳过 / value_norm 保存加载），全量 **71 测试通过**
- ✅ 小编组冒烟（25ep）：**跳过次数=0**，`value_loss` 0.6~0.8（O(1) 正常量级），`value_norm_std≈85`（returns 已归一化）
- ✅ 万吨级短训（3ep）：`loss=0.156` 正常更新，KL 早停幅度 0.015~0.033（PPO 常规范围）

**⚠️ ValueNorm 修复后仍发散 → 第三层根因（SafetyLayer 动作修正破坏 log_prob 一致性）**：
- 现象：500ep 训练 Ep 10 viol 1315 → **Ep 20 viol 112368**（复现修复前发散轨迹），peakCoupler 1940kN，loss 却正常（0.187）
- 根因：`train_env.step` 中 `actions = safety.protect(actions)` **修正后才喂给动力学**，但 `select_actions`/`store_transition`/`update` 均用**修正前动作**的 log_prob → 实际执行策略 ≠ 学习策略 → importance sampling 失效 → 安全层触发越多（viol 越大）→ 梯度方向越错 → 恶性循环
- 为什么阶段一无人机收敛：小编组 safety 触发少，mismatch 可忽略；万吨级长大下坡 safety 频繁触发（紧急制动）→ mismatch 主导
- **修复**（`train_env.py` + `mappo_agent.py` + `train_train.py`）：
  1. `step` 返回 `info['executed_actions']`（安全层修正后的实际执行动作）
  2. 新增 `MAPPOAgent.get_log_prob(state, actions)`：用实际执行动作重算联合 log_prob
  3. 训练循环：`executed = info.get('executed_actions')` 存在时，存储 executed 动作并重算 log_prob（兼容阶段一环境无此字段）
- **验证中**：20ep 短训（日志 `outputs/train_logs/verify_20ep_safetyfix.log`），前 8ep viol 1282 正常未爆（对照修复前 Ep 20 爆 11 万）

**历史教训（三层 bug 链）**：
1. 发散时先查**算法层数值 bug**（归一化/尺度），不要先怀疑超参（lr 调 10 倍无效是强信号）
2. **安全层修正动作必须与实际执行动作的 log_prob 一致**——安全修正不是免费的，必须回传实际动作重算梯度
3. 阶段一收敛 ≠ 阶段二收敛：任何"多一层干预"（安全层/盾/裁剪）都要检查是否破坏 PPO 理论前提


### V5.2 per-agent ratio 修复（真正的 MAPPO 多智能体实现）+ viol 指标 bug（2026-08-14，P1 第16条）

**背景**：V5.1 三层修复后小编组 6 车对照实验仍发散（Reward ~-2700 无改善）→ 回溯 V5.1 中"log_prob 按 num_drones 归一化"修复**本身是错的**。

**根因（第四层）**：正确 MAPPO 是 **per-agent ratio**：
- 每 agent 用自己的 `log_prob` 差算 ratio（`exp(logπ_new − logπ_old)`，各 agent 独立）
- 联合 log_prob = 各 agent log_prob **求和**（= log 联合概率），供 PPO surrogate 使用
- 我 V5.1 的"÷num_drones 归一化"把联合 log_prob 压缩到 1/N 次方 → `ratio≈exp(Δ/101)≈1` → `policy_loss≈0` → **策略不学习** → 随机策略被安全层紧急制动 → viol 爆

**同时发现 viol 指标 bug**：`train_train.py` 中 `ep_viol += info.get('coupler_limit_violations')` 重复累加——info 里该值是 **reset 起累计值**，每步再 `+=` 一次 → 三角累加放大（历史 viol 数值虚高数倍）。修复：直接覆盖取最后一步的累计值。

**修复方案**（`mappo_agent.py`）：
- `select_actions` 返回 **per-agent log_prob 数组**（shape=[num_drones]）而非标量
- `get_log_prob` 同样返回 per-agent 数组（供安全层修正后重算）
- `update()` 改为 per-agent ratio：`ratio = exp(new_log_probs − old_log_probs)`，shape=[batch, num_drones]，surrogate 在 batch×agents 上平均（共享策略 MAPPO 标准做法）
- KL 早停用 per-agent 平均 KL（修复前联合求和被 N 倍放大 → 0.7+ 虚高 → 每轮都早停）

**验证**：
- ✅ 6/6 mappo 测试通过（1 个断言更新：log_prob 从 float 改为 np.ndarray）
- ✅ 小编组 6 车 25ep：viol 从 bug 值 1147 → **真实值 5**，loss 正常（指标 bug 修复生效）
- ✅ 万吨级 20ep 验证：**Ep 10 viol=8.0**（修复前同点 1315 / 发散版爆到 11 万），per-agent KL=0.0153（正常量级，修复前 0.7+），loss 0.191 正常
- ⚠️ **WSL 意外重启（2026-08-14 08:20）杀掉了训练进程**（Ep 10 后中断），同日 `unattended-upgrade` 占 80-95% CPU 抢资源——已停服务 + `setsid nohup` 重启验证，Ep 11-20 结果待确认

**历史教训**：
1. **调试"不收敛"时逐层回溯自己的修复**——V5.1 的"归一化"修复引入新 bug，掩盖了真问题；对照实验（小编组）是定位回归的关键手段
2. MAPPO 多智能体必须用 **per-agent log_prob/ratio**；联合 log_prob 求和只在单智能体或集中式策略场景有效
3. 长时间训练需防 WSL/系统重启中断：`setsid nohup` + 定期 checkpoint；`unattended-upgrade` 等系统服务会抢占 CPU，正式训练前应停止


### V5.3 训练性能向量化优化（2026-08-14，P1 第16条）

**问题**：万吨级（101 车）训练 ~130-180s/ep，500ep 预计 18h，GPU 利用率仅 4-10%（动力学 numpy 计算为瓶颈，且策略前向逐车循环）。

**根因**：三个逐车 Python 循环在每步重复执行，且策略前向 batch=1：
1. `select_actions`/`get_log_prob` 逐车循环（每步 2 次 × 101 次 batch=1 前向）
2. `update()` 内逐车循环（每 epoch 每 mini-batch × 101 次）
3. `_coupler_forces`/`_resistance_forces` 逐车标量循环（n=101）

**修复方案（向量化）**：
- **策略前向**：共享策略下每车 obs 维度相同，把 flatten 状态 reshape 成 `[num_drones, obs_per_drone]` 一次前向（替代 101 次 batch=1）；`update()` 把 `[batch, N*obs]` 改成 `[batch*N, obs]` 一次前向，per-agent log_prob 用 `view` 还原
- **降低前向冗余**：`step` 里安全层未修正动作时（`actions_modified=False`），复用 `select_actions` 的 log_prob，跳过 `get_log_prob` 二次前向；仅安全层实际修正时才重算
- **动力学向量化**：`_coupler_forces` 用相邻差分数组（`pos[1:]-pos[:-1]`）+ `np.where` 死区一次算完 n-1 个车钩力；`_resistance_forces` 内联 Davis 公式，提取每车参数为数组一次算完

**验证**：
- ✅ 全量 71 测试通过（无回归，数值与向量化前一致）
- ✅ 万吨级 3ep 短训：**50.36s（16.8s/ep）**，优化前 ~130-180s/ep → **提速约 8-10 倍**，500ep 从 18h 降到约 2.3h
- ✅ 训练质量正常：Ep3 `loss=0.118`、`viol=11.3`（未发散）、best -1473.4

**历史教训**：
1. **共享策略多智能体的前向必须整批向量化**——N 个 agent 的 obs 拼成 `[N, obs_dim]` 一次前向，比 N 次 batch=1 快 10 倍以上（GPU 利用率 4%→80%+）
2. **安全层未触发时不要重复前向**——用 `actions_modified` 标记判断，避免 `select_actions` 和 `get_log_prob` 各算一次同样的 log_prob
3. 动力学逐车循环能用 numpy 差分/广播向量化的就向量化，注意保持数值一致（用测试回归保障）


### V5.4 万吨级 500ep 正式训练发散诊断（2026-08-14，P1 第16条，待决策）

**现象**（性能优化后正式长训，日志 `baseline_500ep_v53.log`，130ep 后停止）：
| 回合 | Reward | peakCoupler | viol | loss |
|:--|:--|:--|:--|:--|
| Ep 10 | -2680.7 | 1573 kN | 10.9 | 0.195 |
| Ep 30 | -3351.6 | 3456 kN | 2255 | 0.198 |
| Ep 70 | -3221.8 | 2364 kN | 1805 | 0.272 |
| Ep 110 | -3465.4 | 3812 kN | 2211 | 0.402 |
| Ep 130 | -3483.0 | 3766 kN | 2166 | 0.401 |

**关键观察**：
- Reward 稳定在 -3200~-3480 震荡，**best -1473.4 从初始种子后从未更新**（130ep 无任何改善）
- **peakCoupler 持续 2000~3800 kN**，远超车钩力上限 1000 kN（严重超限）
- loss 正常更新（0.2→0.4），说明数值层无 bug，是**策略学不到平稳控制**

**根因分析（非数值 bug，是设计缺陷）**：
1. **安全层只拦牵引、不拦制动**（`safety_layer.py` 规则2）：车钩力超限时仅处理 `actions[i] > 0`（牵引），对 `actions[i] < 0`（制动）完全放行。而长大下坡 + 万吨级（101 车）场景下，**车钩力爆表的主因恰恰是剧烈制动**（空气制动波速 200m/s 沿车列传播 → 前车先减速、后车惯性前冲 → 纵向冲动）。安全层守不住 1000 kN 上限。
2. **奖励信号太弱**：`violation_penalty = -2.0` 是常数（`_calculate_reward`），冲动项权重仅 0.15；速度/间距误差主导奖励，策略没有足够梯度学会"平稳制动"。
3. **阶段一小编组收敛 ≠ 万吨级收敛**：4 车时冲动小、安全层不触发、不破坏 PPO；101 车时冲动是本质性的，安全层/奖励缺陷被放大。

**待决策方案（暂未改代码）**：
- 方案 A：强化安全层——车钩力超限时也抑制制动动作（限制制动幅度/主动缓解），让安全层真正守住 1000 kN
- 方案 B：强化奖励——`violation_penalty` 从常数 -2.0 改为按超限幅度成比例惩罚 + 提高冲动项权重
- 方案 C：A+B 组合（安全层硬约束 + 奖励软引导）

**历史教训**：
1. **安全层的"最小干预"必须有对称性**——只拦牵引不拦制动，等于把制动产生的纵向冲动风险完全交给 RL 自己学，而 RL 在稀疏/弱奖励下学不会，安全层形同虚设
2. **车钩力 1000 kN 是"双用途"指标**（安全约束 + 最终评估），若安全层守不住它，则最终评估指标也无意义——必须先保证安全层能守住，再谈 RL 优化


### V5.5 安全层对称拦制动 + 奖励梯度修复（2026-08-14，P1 第16条，进行中）

**实施（方案 C 规则式）**：
1. **安全层对称拦制动**（`safety_layer.py` 规则2）：车钩力超限时，从"仅拦牵引 `actions[i]>0`"改为"对称拦所有非零动作 `actions[i]!=0`"，统一钳制为 0（惰行）。
2. **奖励超限惩罚成比例**（`train_env.py` `_calculate_reward`）：`violation_penalty` 从常数 `-2.0` 改为 `-5.0 * over_ratio`（超限幅度成比例），冲动项权重 0.15→0.2。

**验证**：
- ✅ 新增 4 测试（拦制动/对称性/奖励梯度/无超限无惩罚），全量 **75 测试通过**
- ✅ 随机策略诊断：安全层拦截 61 步、**peak 814.8 kN、viol=0**（守住上限）

**⚠️ 关键发现：安全层仍拦不住"已传播的空气制动"（根本性设计缺陷）**：
| 动作模式 | peakCoupler | 安全层拦截步数 | viol |
|:--|:--|:--|:--|
| 随机动作 | 814.8 kN | 61 | 0 |
| **全列制动 -1** | **1292.1 kN** | **0** | **79** |
| 全列牵引 +1 | 532.7 kN | 0 | 0 |
| 仅机车制动 | 1292.1 kN | 0 | 79 |

**根因（V5.5 深层）**：安全层只能钳制"动作"，但**制动通过空气制动系统（离散档位 EB/SB + 波速传播）产生的是状态性、持续性制动力**——`train_env.step` 里负动作被拆分为"电制动（仅机车）+ 空气制动（队首传播）"，空气制动档位一旦发出就沿车列传播持续生效。**钳制动作 ≠ 撤销已传播的空气制动**，所以安全层对"全列制动"型动作完全无法拦截（modified=0），压钩力飙到 1292 kN。

**为什么训练爆到 3500 kN**：训练策略学会"持续发制动 → 空气制动持续 EB → 压钩力累积"，安全层无能为力；随机动作正负混杂、牵引制动互相抵消反而冲动小。

**待决策（下一步）**：
1. 安全层需**直接干预空气制动状态**（而非仅钳制动作）：车钩力超限时主动缓解空气制动（`_reset_air_brake_command`），但需评估这是否破坏"自动控制=RL 控制器"的定位
2. 或**限制空气制动档位**：禁止策略在车钩力接近上限时发出 EB 级制动（动作空间/奖励层约束）
3. 或**接受安全层只能软约束**，把车钩力硬上限交给 CBF（中期理论方向）


### V5.6 架构重构：列间 MARL + 列内底层控制器 + 编队间距 bug（2026-08-14，重大方向纠偏）

**背景（用户纠正核心架构）**：
- **"0+1" = 1 台动力机车 + ~100 节拖挂**（不是前后两台动力）
- **多智能体 = 多列万吨列车（每列 1 智能体，列间编队）**；列内（1机车+100拖挂）= 单列控制，非多智能体
- **当前代码 `train_train.py` 实现错误**：把 101 节车厢当独立智能体（`num_drones=101`）→ 这是训练难收敛 + 车钩力爆表的**真因之一**（错误的"伪多智能体"粒度）
- **新增底层控制器**（业界做法，用户决策）：层级一 RL 定策（目标速度）+ 层级二底层控制器安全执行

**架构重构（新代码）**：
- `src/controllers/low_level_controller.py`：`TrainLowLevelController`（列内底层控制器，PID 速度跟踪 + 车钩力安全钳制）
- `src/environments/train_fleet_env.py`：`TrainFleetEnv`（多列编队环境，智能体=每列，动作=目标速度，obs 含车钩力统计）
- `src/trainer/train_fleet.py`：列间 MARL 训练入口（复用 MAPPOAgent，num_drones=列数）

**关键 bug：编队初始间距错误（导致 Reward 爆炸 -16 万）**：
- **现象**：30ep 训练 Reward 单调恶化（-22396 → -76493 → -135952），但 peakCoupler 守住（558→706kN）、viol=0、loss 正常
- **根因**：`TrainFleetEnv.reset` 用 `set_initial(pos=pos - i*target_gap)` 平移整列，但**列内 pos 本身是负方向排列**（前车0→后车-100），平移后列间首尾相接（间距=0m 而非 100m）。间距误差 obs 恒为 -100，`-0.3*gap_err` 贡献巨大不可消除的负奖励 → 策略无法学习。
- **附带问题**：reset 跨轮次累积平移（`set_initial` 基于当前 pos，导致多次 reset 后间距翻倍）
- **修复**：`__init__` 保存每列基准 pos（`_base_pos`），reset 从基准重建位置；跟随列平移量 = 列内长度 + target_gap（前车尾到本列头 = 100m）
- **验证**：间距从 0m → 100m（正确），obs 间距误差从 [-100,-100] → [0,0]，reward 从 -21.89 → **-1.89**（正常量级），6 测试通过

**历史教训**：
1. **编队间距要用"前车尾到本列头"定义**（车钩空隙），不是简单整列平移——列内 pos 负方向排列会吃掉 target_gap
2. **reset 必须从基准位置重建，不能基于当前 pos 增量平移**（跨 reset 累积）
3. **Reward 爆炸先查 obs/环境逻辑**（间距 bug），不要只怀疑算法——车钩力守住、loss 正常、但 Reward 单调恶化 → 优先查环境状态构造

### V5.7-V5.9 列间 MARL 架构演进 + 论文调研对齐（2026-08-15，P1 第16条）

**背景**：正确架构（多列编队，每列=智能体，列内底层控制器）跑通后，列间 RL **"学无可学"**（Reward 稳定、KL早停=0、best 不更新）。

**场景特性认知（V5.8，经诊断验证）**：
- 长大下坡列车**无法牵引超速，只能制动降速**：目标20→20.6（限速锁死）、目标25满牵引→仍20.6、目标15→15.6
- 列间 RL 价值 = **协同制动策略**（多列协同制动避免追尾+车钩力+安全间距），**不是牵引能耗优化**（下坡不用牵引，能耗信号弱）

**论文调研（Hua2024 / Zhang2021，全文提取）**：
- **Hua2024**（CACC 车队 MARL + 稳定+能耗协同）：
  - 动作：RL 选 OVM 控制器 4 组离散参数（不是直接控牵引）
  - 奖励：`R = w1(d-d*)² + w2(v-v*)² + w3u² + w4(2ds-d)² + w5P`（间距+速度+**加速度舒适性**+**安全势场**+**能耗功率**）
  - 安全：间距<2ds 势场惩罚，间距≤1m 惩罚1000终止
- **Zhang2021**（列车编队 MADRL，leader-follower）：
  - 动作：每列加速度 `a∈{a+,0,a-}`（离散3档）
  - 列车模型：**单质点**，忽略车钩力
  - 奖励：基于 APF 势场的双子奖励 `rn=f(en-1,n, vn-1,n)`
- **关键结论**：业界让列间 RL 有协同价值的关键 = ①**奖励含舒适性（加速度）项**（底层 PID 不优化，是 RL 增量）②动作粒度更细（加速度/控制器参数）③安全用势场

> ⚠️ **纠错（2026-08-20，用户纠正）**：Zhang2021 是**地铁平直线路、单质点、忽略车钩力、无坡度**场景，其 **APF 势场控制器**（`tanh(间距误差)+tanh(速度差)`）假设车辆可自由±加减速，**与我们"朔黄线长大下坡 + 循环制动 + 车钩力"场景物理不符**。长大下坡列车**无法牵引超速、只能制动降速**（向下可制动、向上无牵引），±对称的 APF 修正会破坏循环制动的离散档位节奏。
> **本项目仅借鉴其两点**：①"控加速度"而非"控目标速度"的动作粒度（`get_action_accel`，已实施）；②"安全势场惩罚避免追尾"（已实施）。**不得把 Zhang2021 的 APF 势场控制器当作本项目的列间解耦/协同方案**——正确分层见 PROJECT_PIPELINE 4.0（列间 RL 宏观协同 + 列内规则循环制动 + 车钩力安全层），不引入 APF 势场控制器。

**方案优化（V5.9，已实施）**：
- 加入**舒适性（加速度）奖励项** `-0.3 * mean(accel²)`（对齐 Hua2024 w3u²）
- 保留安全势场（间距<40%目标→惩罚）+ 追尾硬惩罚 + 车钩力约束（创新点）
- 扰动场景（领航车突发减速到 12m/s）保留，跟随车学协同平稳制动

**训练验证中**：60ep 舒适性奖励（日志 `fleet_60ep_comfort_v59.log`）

**历史教训**：
1. **底层控制器太强会抢走 RL 工作**——"目标速度"动作被 PID 消化，RL 学无可学；需加入底层控制器不优化的目标（舒适性/能耗）让 RL 有增量价值
2. **业界列间 RL 不是控"目标速度"而是控"加速度/控制器参数"**——动作粒度决定了有无学习空间
3. **长大下坡场景特性（只制动不牵引）决定 RL 价值定位**——协同制动 + 舒适性，而非牵引能耗

### V5.10 方案 B：加速度动作空间解决"学无可学"（2026-08-15，重大突破）

**问题**：列间 RL 用"目标速度"动作，但长大下坡列车物理极限（16.7m/s）低于目标（20m/s），导致动作 +1/0 饱和在同一物理状态，Reward 无区分度 → 策略不学习（KL早停=0、best 不更新、Reward 平线）。

**决定性诊断**：动作+1(目标25)和动作0(目标20) 60步奖励完全相同（-60.5）、末速相同（16.7）→ 动作空间与物理极限脱节，PPO 无法从 <0.1/步 的弱信号学习。

**修复（方案 B，对齐 Zhang2021 每列控加速度 / Hua2024 OVM 参数）**：
- 动作从"目标速度"改为"**目标加速度**" `a ∈ [-max_accel, max_accel]`
- 列内底层控制器新增 `get_action_accel`：目标加速度 → throttle（线性映射 + 车钩力钳制）
- 动作直接影响物理（列车加速度），有真实学习区分度

**验证（60ep，扰动协同制动场景）**：
| 指标 | 目标速度（旧） | 加速度（新） |
|:--|:--|:--|
| Reward | 平线 -900 | **-885 → -546（改善40%），单调下降** |
| best | 从不更新 | **持续更新**（-784→-598→-567→-525→-466）|
| KL早停 | 0 | 0（但Reward真实改善，小步学习未触发阈值）|
| peakCoupler | 守住 | 844→1109kN（偶尔略超，viol~1）|

**结论**：动作粒度决定 RL 有无学习空间——"目标速度"被物理锁死，"加速度"直接影响物理。**列间 MARL 首次真正学习协同制动策略（Reward 单调改善 40%）**。

**后续待处理**：peakCoupler 偶尔超 1000kN（加速度更激进导致车钩力略超），需在奖励/安全层再平衡。

**历史教训**：
1. **RL 动作空间必须与物理可达范围匹配**——"目标速度"超出物理极限（16.7 vs 20）导致动作饱和，RL 学无可学
2. **动作粒度决定学习空间**——控"加速度"比控"目标速度"有真实梯度（对齐 Zhang2021/Hua2024）
3. **Reward 平线 + best 不更新 + KL早停=0 = 动作空间问题**（非奖励/算法问题），先查动作对物理的影响

### V5.12 对比实验 + 车钩力严格守住（2026-08-15，论文核心结果）

**对比实验框架**（`src/evaluation/evaluate_fleet.py` + `run_compare.py`）：

**对比实验结果（扰动 -0.5，mean±std，3 种子）**：

### V5.20 诊断：车钩力是否在群组协同时才凸显？（2026-08-16）

**背景**：grill-me 拷问中构造核心命题——"车钩力 = 群组协同瓶颈，单列独立守住、群组协同逼近上限"。用诊断脚本验证该命题是否在当前场景/策略下成立。

**诊断脚本**：`src/evaluation/diagnose_coupler_scene.py`（保留供复现，非临时脚本）
**数据落盘**：`outputs/diagnostics/coupler_scene_20260816_111808.csv`
**运行命令**：`python src/evaluation/diagnose_coupler_scene.py --seed 0 --disturbance_accel -0.8`（WSL, traffic_rl）

**诊断结果（seed 0，扰动 -0.8）**：

| 工况 | 车钩力峰值 | 超限 | 间距误差 | 速度误差 |
|:--|:--|:--|:--|:--|
| A1 单列独立（无扰动） | 532.7 kN | 0 | — | 3.37 m/s |
| A2 单列独立（强制制动 -0.8） | 978.2 kN | 0 | — | 6.99 m/s |
| E 群组协同（无扰动） | 532.7 kN | 0 | 5.5 m | 3.37 m/s |
| C 群组协同（扰动） | 978.2 kN | 0 | 7.2 m | 4.57 m/s |
| D 群组协同（扰动 + 忽略车钩力） | **1140.4 kN** | **8** | 7.2 m | 4.59 m/s |

**归因分析（决定性，逐列数据见 CSV）**：
- **扰动效应** = C(群组扰动) − E(群组无扰动) = **445.5 kN**；单列扰动效应 = A2 − A1 = **445.5 kN（完全相同）**
- **群组效应（无扰动）** = E − A1 = **0.0 kN**
- **群组效应（有扰动）** = C − A2 = **0.0 kN**
- 车钩力压力集中在领航车（`[978, 532, 532] kN`），跟随车不受影响

**核心结论（如实记录，含失败）**：
- ❌ **"群组协同会放大车钩力、车钩力是群组瓶颈"的命题，在当前场景/策略下被数据否定**——车钩力放大 100% 来自扰动制动本身（单列/群组同样放大 445.5kN），**群组协同贡献为 0**。
- **原因（期望 vs 实际）**：期望"群组为保持间距而剧烈协同制动 → 放大列内冲动"；实际 `baseline_no_coupler_mar` 策略温和跟随（间距误差仅 7.2m），跟随车不产生列内冲动，故车钩力压力集中在领航车扰动制动本身。
- ✅ **但发现真实价值信号**：D 工况（忽略车钩力）超限 **1140.4 kN / 8 次**，证明"车钩力建模必要性"真实存在——但它目前体现在**单列遇扰动时的安全兜底**，**未通过"群组协同"体现**。
- 📌 **下一步方向**：需构造"群组协同主动制造车钩力压力"的场景，让车钩力成为真正的群组瓶颈：
  1. 领航车**连续制动-缓解循环**（非单次扰动），制造反复纵向冲动
  2. **更紧的列间间距**，迫使跟随车剧烈响应
  3. 跟随车**快速补位**（间距缩小后加速跟上，产生列内拉钩力）
- **对论文定位的影响**：若无法构造"群组协同放大车钩力"场景，则"车钩力"与"多列群组"两个创新点的耦合仍不成立，需重新设计场景或调整创新点表述。

**历史教训**：
1. **假设必须用仿真验证**——grill-me 推理看似严密，但"群组放大车钩力"在当前场景下被数据证伪；先诊断再下结论
2. **归因要区分"扰动效应"和"协同效应"**——加入单列强制制动(A2)、群组无扰动(E)两个对照工况，才定位到"放大来自扰动而非群组"
3. **车钩力建模价值真实存在（D 超限）但载体错误**——当前体现在"单列安全兜底"，需重新设计场景让载体是"群组协同"

### V5.21 E3 结构性根因分析 + 三项修复（2026-08-16，M1 训练决定性验证）

**背景**：M1 群组 MAPPO 训练多次失败（v1 超速97%、v2/v3 车钩力爆炸、v4 协同间距1106m）。用 subagent 做系统性根因分析，发现**3 个结构性根因**（非调参可解）。

**根因1（最根本，死锁）**：`SafetyLayer` 规则2"车钩力超限→钳制为0（完全释放）"与"长大下坡必须制动降速"形成死锁：
- 下坡超速 → 规则1强制制动(-0.75) → 空气制动波速传播延迟(单列1221m/200m/s≈6.1s) → 队尾车钩力超限 → 规则2完全释放 → 列车加速超速 → 又强制制动 → 无限震荡
- E3 实测：车钩力超限暴涨到 625 次、峰值 1439kN

**根因2**：RL 探索期随机输出 throttle<-0.8 → EMERGENCY 满制动 + 波速延迟 → 车钩力爆表。第1层固定 -0.75(SERVICE) 温和制动所以成功。

**根因3**：obs 缺坡度空间分布（只取队首坡度，列车跨1.2km后半段未知）、前列状态（协同预判）、车钩力位置。

**物理可行性验证（决定性）**：
- 单列 vs 多列规则循环制动结果几乎一样（都掉到3.7m/s）→ 掉速非列间耦合，是规则策略+剖面问题
- **第1层模型（train_cyclic_braking）在真实剖面验证**：平均71km/h、速度[64,87]、**车钩力峰值仅150kN/超限0** → 证明真实剖面可行、车钩力可守住
- 惰行：超速36%、车钩力107kN；规则循环制动(-0.5)：掉速3.7m/s、车钩力1013kN → 规则控制器都不行，RL 有巨大提升空间

**三项修复（82测试过）**：
1. `low_level_controller.get_action_accel`：RL 动作制动深度限制到 [-0.75,0]（SERVICE 档），禁探索期打满 EMERGENCY
2. `safety_layer.protect` 规则2：车钩力超限时牵引钳制为0、**制动降低到 MIN 档(-0.3)保留制动**（原完全释放→死锁）
3. `train_fleet_env` obs 增强：obs_dim 6→9，新增位置/队尾坡度/前列速度

**v4 训练（seed0）成果**：

### V5.27 缓解波传播 bug 修复（2026-08-18，决定性，问题彻底解决）

**背景**：用户纠正——缓解波物理客观存在，丢弃模型不可用。朔黄线非核心需求，继续找可行方案。

**根本 bug 定位（精细诊断）**：
- 缓解后监测：active 车 4→14 增加（应减少到0）、缓解波 delay 恒定 6.0 不递减、制动力不归零
- **两个 bug**：
  1. `_advance_air_brake_propagation` 反向制动传播：缓解时尾部仍 active → 反向重新激活已释放的前车
  2. `step_vehicles_ed_ab` 缓解逻辑：只要 `np.any(active)` 每次 step 都 `_reset_air_brake_command` → 反复重置缓解波 delay → 缓解波永远传播不完 → 缓解不生效 → 持续制动 → 掉速

**修复**：
1. 缓解状态（`_air_brake_releasing[0]`）禁止反向制动传播
2. 缓解波传播中（`_air_brake_releasing[brake_origin]`）不重复 `_reset_air_brake_command`

**修复后验证（朔黄线缓解波循环制动）**：
| 配置 | 车钩力峰值 | 循环制动 | 平均速度 |
|:--|:--|:--|:--|
| 制动80/缓解50 | **740kN ✅** | ✅ | 63.6km/h |
| 制动80/缓解55 | **740kN ✅** | ✅ | 68.1km/h |
| 制动85/缓解55 | **733kN ✅** | ✅ | 65.9km/h |

**第1层缓解波训练成功**：Ep10 Reward +7349，车钩力503kN/超限0，速度[64,70]km/h不掉速。

**决定性结论**：朔黄线 + 缓解波 + 1+0单机 + 循环制动**完全可行**（车钩力≤740kN）。**之前所有"车钩力超限/掉速/不可行"结论，都是缓解波传播 bug 导致**。无需换线/EOT/接受超限。
