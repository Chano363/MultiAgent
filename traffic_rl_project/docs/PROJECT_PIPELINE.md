## 三、通用开发流程（两个阶段共用）

每阶段遵循同一套方法论，后续任何新任务（列车编队）按此流程执行：

```
① 文献调研        → 明确物理模型与算法选型的依据
② MDP 建模        → 定义状态 / 动作 / 奖励函数
③ 环境搭建        → 基于专业仿真器封装 Gym 接口（禁止手动/mock 环境）
④ 基线训练        → 先用成熟算法跑通链路，验证环境与奖励合理性
⑤ 算法适配        → 按任务特性选型（多智能体用 CTDE）
⑥ 奖励与超参迭代  → 一次只改一个变量，记录结果
⑦ 评估与消融      → 确定性推理、组件贡献度分析
⑧ 成果固化        → 报告 + 检查点 + 图表 + 配置快照
```

**每阶段的验收标准**：训练收敛稳定（无策略坍缩）→ 指标达到阈值 → 消融实验说明组件贡献 → 报告可复现。

### 4.0 下一阶段工作方针（2026-08-20 最终确认，★★★★★ 不可偏离）

> **本小节是当前阶段所有工作的最高指导方针。任何任务、实验、代码改动都必须对照本方针执行，不得偏离。**

**核心定位（用户多次强调，绝不允许改动）**：

- 论文题目：面向长大下坡场景基于多智能体强化学习的**重载列车群组自动控制方法**

- 三大支柱：**循环制动 + 多列群组协同 + 车钩力约束**（分层 MARL）

- 现有长大下坡 RL 工作中 Zhang2024/Liu2021 忽略车钩力（Wang2025 ICIRT 例外：单列但车钩进 reward，属边界不算空白，2026-10-13 复核修正）→ 本项目的创新空间

**正确场景理解（2026-08-20 用户最后纠正，关键）**：

- ❌ **不是**"更紧间距制造压力"或"系统强制制动制造车钩力压力"——这是此前多次失败（协同价值=0）的根源

- ✅ **正确逻辑**：朔黄线长大下坡**天然需要循环制动**（单列本身产生车钩力）+ **多列车需保持安全间距**（虚拟耦合）**双重需求天然并存**

- 各列循环制动**相位天然错开**，跟随车为保持间距需**配合前列的制动/缓解节奏** → 协同价值由**场景天然驱动**

- **不引入人为扰动**（真实线路本身驱动协同）

**必须验证的增量（下一阶段核心任务）**：

- **M1（多列群组协同 + 车钩力约束）** vs **M3（单列独立，只循环制动不协同）**

- 证明 M1 相对 M3 的**增量价值**（间距保持 + 安全，车钩力作为贯穿约束）

- 场景：**主训练剖面 = 朔黄线 `shuozhou_ningwuxi_beidaniu_49km`（宁武西→北大牛真实纵断面 49.6km，2026-10-12 取自统一线路表 `朔黄铁路_完整线路信息表_表3表4补充版.xlsx` 重建，替代原 `shuozhou_real_53km` 53.2km 与手写 `shuozhou_23800` 23.8km）** + 多列虚拟耦合 + 长大下坡循环制动

**已完成的关键积累（支撑本方针，勿推翻）**：

- 缓解波传播 bug 已修复（缓解波物理保留），朔黄线 + 1+0 单机 + 循环制动车钩力 740kN 守住

- 分层框架：层级二 RL 第1层策略控速（warm start 自规则）+ 层级一 δ 协同（E18 avg+2.1万稳定）

- 限速区间 \[40,80]（行业 + 论文 + 物理三重依据）

- 离散档位动作 + 规则循环制动 warm start + 循环引导

**工作方针执行检查表（每项工作前对照）**：

1. 场景是否为"朔黄线真实剖面 + 多列保持间距 + 循环制动"天然驱动？
2. 是否引入了人为扰动？（→ 应改为天然驱动）
3. 对比是否锚定 M1 vs M3（协同增量）？
4. 车钩力是否作为贯穿约束（而非人为制造超限）？

**核心逻辑链澄清（2026-08-20 用户纠正，务必记住，勿再搞混）**：

- ① **车钩力在列内处理**（每列内部车厢间机械钩缓，制动-缓解产生）——**不冲突**

- ② **编队的价值 = 维持各列之间距离**，而维持距离需要**循环制动**（长大下坡必须制动控速）

- ③ **编队 → 循环制动 → 列内车钩力变化**：一列为配合编队距离而制动/缓解 → 该列内部车钩力变化

- ④ **核心创新 = 多列编队协同（为保持间距的循环制动节奏配合）影响/约束每列内部车钩力**

- **"错开"为何相关**：各列循环制动相位/节奏不同（前列先制动、后列配合）→ 某列因配合间距急制动 → 列内车钩力放大；**协同价值 = 保持间距的同时控制/最小化每列车钩力**

- **正确对比**：M1（协同协调制动节奏保持间距 + 控车钩力） vs M3（每列独立按速度循环制动，不管间距 → 追尾急制动 → 车钩力大/牺牲速度）

- **与 Zhang2024 区别**：Zhang2024 单列循环制动，无"保持编队距离"约束；**我们的创新 = 在"多列必须保持间距"约束下协同循环制动，同时守住每列车钩力**

- ⚠️ **勿把车钩力当成"多列之间"机械耦合**（会陷入"多列无机械钩挂"的困惑）；实际是"多列协同→影响每列循环制动节奏→影响该列内部车钩力"

### 4.2.6 速度维持优化计划（低40掉速瓶颈，2026-08-21，当前执行）

**背景**：步骤③评估显示 M1/M3 低40占 26%（掉速惩罚重），整体 reward 为负。这是当前唯一阻塞 M1 vs M3 增量"净为正"的瓶颈。修复编码根因后，协同增量已由负转正（M1 -10123 vs M3 -13407），但**速度维持不足**使整体 reward 仍为负，无法作为论文正向结果。

**根因分析（低40掉速）**：`get_action_cyclic_braking` 用 `v_min=40km/h` 作为缓解触发阈值（`vel <= eff_v_min` 才缓解）；万吨列车在长大下坡（-10‰）上一旦开始制动，**缓解后因下坡重力惯性继续减速穿越 40km/h**（缓解是渐变衰减需时间 + release\_throttle=0 惰行，重力仍拖动）；第1层 RL 策略（warm start 自规则）学的缓解时机可能偏晚，未在跌到 40 前及时缓解。

**优化方案（3 条，按预期收益/风险排序）**：

| 方案 | 内容                                                                    | 预期收益           | 风险                     | 优先级 |
| :- | :-------------------------------------------------------------------- | :------------- | :--------------------- | :-- |

### 4.2.7 多列长运行满制动失效专攻计划（2026-08-21，当前专攻）

**背景**：方案A后健康场景固化（M1 +44200、低40=0、车钩力892kN），但扩展评估到 6000 步（列车走13km）时，速度飙到 **117km/h**（超80上限），且**多列满制动不减速**。

**已确认事实**（详见 VALIDATION\_BASELINE「诊断-2026-08-21 长距离超速」）：

1. 限速安全层配置正确（max\_speed=80km/h），超速时 protect 强制制动（已修 -0.75），第1层策略输出满制动 -1.0
2. **fresh 状态**下单列 vs 多列满制动**表现一致**（都 95→80 减速）→ 多列动力学本身无 bug
3. \*\*长运行后（4100步 δ=0）\*\*多列满制动失效（95→96 加速），单列仍减速（95→84）→ **状态积累问题**
4. 制动力相关属性（braked\_weight\_ratio/max\_ed\_ratio/ab\_sources/brake\_wave\_speed/eot）单列多列全部相同

**核心矛盾**：同一动力学（train.py）、同一配置，长运行后多列满制动失效而单列正常。差异仅在多列 trains\[0] 经历长运行（缓解波传播/车钩力状态残留）。

**假设（待验证）**：**H1** 缓解波传播状态 `_ab_propagation`/`_release_propagation` 长运行后残留 → 制动命令未正确传播到尾部 → 制动力不足；**H2** 车钩力-制动力耦合（长运行下车钩力状态影响制动力应用）；**H3** dt 积分累积误差在长运行时放大；**H4** 坡度查询 bug（列车横跨多坡段，grade 计算错误导致制动力低估）。

**排查步骤（按优先级）**：1) 在 4100 步长运行后打印各车厢实际制动力 `_brake_force`、空气制动档位、缓解波传播数组 → 定位是否尾部制动力丢失；2) 对比长运行后 vs fresh 的动力学内部状态（`_ab_propagation`、车钩力、pos）；3) 用**恒定坡度**在长运行后满制动 → 隔离 H4；4) 重置缓解波传播状态后满制动 → 隔离 H1；5) 若定位到状态残留 → 修复（reset 时清空传播状态 / 修正传播逻辑）。

**验证目标**：长运行后满制动仍能限速（与 fresh 一致），6000 步不超速到 117。

**专攻结果（2026-08-22）**：3 种补丁修复（打断缓解/逐节清releasing/激活恢复制动力）均陷入"掉速+车钩力爆炸 vs 超速"两难，已全部回退。论文调研（樊运新气体流动模型）指出根因是**分离状态机**（active/releasing/release\_frac 互相阻塞），正确方向是**重构为单一"缓解-制动压力渐变"**（对齐樊运新模型）。详见 VALIDATION\_BASELINE「诊断-2026-08-22 论文调研」。

### 4.2.8 最终战略：分层控制架构重构（放弃 RL 学单列循环制动，2026-08-22，当前执行）

**背景（战略纠偏）**：v2 樊运新压力模型重构（物理正确）但 RL 不可学；多次 RL 循环制动（连续/离散/warm start/循环引导）均失败（MEMORY.md L72）。论文调研（Zhang2024/Tang2020）确认**领域标准 = 重载列车 RL 用离散档位动作 + 规则循环制动**；Zhang2024 用 DQN 学循环制动但**忽略车钩力**（单质点）——我们建模车钩力（创新点），不能照搬。**结论**：让 RL 学单列循环制动是结构性失败路线（缓解波长时延 6s → PPO 信用分配失效 + 车钩力多体强耦合 → 探索即爆炸），**彻底放弃**。

**最终架构（不重构缓解波动力学，重构分层控制）**：

```
第1层（单列微观控制）：规则循环制动 get_action_cyclic_braking（已验证 523kN 最优）
                     + 车钩力安全层（≤1000kN）。【不用 RL】
第2层（多列宏观协同）：RL 只输出"协同阈值偏移" v_max_adj/v_min_adj
                     （配合前列制动/缓解时机、保持间距），
                     通过规则循环制动阈值间接作用，不直接叠加 throttle。
                     【RL 的正确用武之地 = 宏观协同，不是微观控速】
```

**为什么这样**：第1层规则循环制动=领域最优（Zhang2024 也是学这个，直接规则化）；第2层 RL 阈值协同=E17 方向（v\_max\_adj/v\_min\_adj 不破坏规则循环制动），但需**限制协同动作范围**（±5km/h）避免 E17 探索到极端阈值；车钩力贯穿=规则循环制动产生 + 安全层约束（创新点保持）。

**重构步骤**：

1. `HierarchicalController.base_throttle`：从"第1层 RL 策略控速"改为"规则循环制动"（`get_action_cyclic_braking`）
2. 第2层协同动作：从"δ 连续叠加 throttle"改为"v\_max\_adj/v\_min\_adj 阈值偏移"（限制范围 ±5km/h）
3. 训练/评估脚本适配（train\_fleet.py / evaluate\_m1\_m3\_long.py 的动作空间）
4. 重训第2层 M1 + 重评估 M1 vs M3

**验证**：83 测试过；规则循环制动 523kN；重评估 M1 vs M3 健康场景协同增量。

**检查表**：场景=朔黄线真实剖面+多列+循环制动；不引入人为扰动；对比锚定 M1 vs M3；车钩力贯穿约束；**不重构缓解波动力学（train.py 保持 git 基线）**。

#### 公平版 MPC 实现要点（2026-08-30 已实现 + 冒烟验证）

- **形态（关键转向）**：采用**直接每列目标加速度**（连续控制的传统形态，非分层模式），而非最初锁定的"coor\_adj 阈值顾问 + 分层同架构"。原因（冒烟实测）：coor 仅移动循环制动触发阈值 ±1.5km/h，而制动事件在分钟级、预测时域（秒级）"看不到"制动相位 → 阈值顾问式 MPC 恒输出 0（退化为无协同），不公平弱化传统方法。传统 MPC 的真实形态是直接命令加速度。

- **实现**（`src/controllers/fair_mpc_controller.py`，`FairMPCController`）：物理列模型预测 = Davis 残差标定 + 坡度 + 加速度命令演化速度/位置/间距（列间耦合）；控制分块（B=4 × block=8 步 ≈ 3.2s 时域）→ 少量决策变量，纯 Python SLSQP 可解；显式硬约束（SLSQP ineq）= 列间间距 ≥ gap\_min + 车钩力代理 ≤ 1000kN；滚动时域 = 每步求 SLSQP、仅施加第 1 块、记录每步求解耗时。

- **冒烟验证（40 步 + 200 步实测）**：无 NaN、控制非平凡（领航列重制动 / 跟随列滑行，间距稳定 178-183m）、200 步 reward +3206、超80/低40=0%、车钩力峰值 400kN、追尾 0、每步求解 117ms（3000 步 ≈ 6min/seed）。

- **公平性**：MPC 与 M-MARL 共用同一环境 SafetyLayer（车钩力最终物理强制一致），差异仅在"控制器来源"（模型驱动在线优化 vs 无模型分层策略）。

- **与论文对比叙事**：主表列 = M-MARL / No-C / M-MPC / DQN-fair（+Coast），立"无模型分层 MARL vs 传统模型驱动 MPC"创新锚点。

#### 公平版 MPC 压力场景结论（2026-08-30 实测，5 seed 随机化初态）

**\[结论]**：M-MPC 在短程（200 步冒烟，reward +3206、0 追尾）可控，但在**长距离循环制动区（朔黄线主剖面 3000 步，初态 55-75km/h 随机化）直接崩盘**——reward −258,831±116,023、低40 占比 70.8%、车钩力峰值 1,431kN（超 1000kN 上限）、间距min −9m（追尾 330 步），而 M1（MARL）同协议 reward +35,464±966 / 0 追尾。**机理：MPC 滚动时域仅 B=4×8 步≈3.2s，无法预见分钟级循环制动相位（"缓坡蓄速→陡坡提前减"的跨分钟节奏），全程仅 4.2 次循环制动、速度崩溃至下限之下，间距/车钩力随之劣化**——这是"滚动时域短视野 vs 无模型全局策略"的决定性实证，也是 M-MARL 相对传统模型驱动 MPC 的核心差异。已落盘 `outputs/mpc_pressure_5seed_20260830.txt`（带时间戳，不覆盖）；留痕见 VALIDATION\_BASELINE「诊断-2026-08-30 MPC压力场景对比」。

### 双人分工与合并方案（2026-10-12，我=单车车钩力侧 / 队友=编队侧）

> 目的：两人并行不互相踩、合并时能对得上。立论/安全分层口径见 `RESEARCH_POSITIONING.md` §1.7（**唯一出处**，本节只讲分工与合并操作）。

**一、分工边界（按模块划，不按指标划——指标是共用的，模块才有 owner）**

| 侧 | 负责模块（改动前先看对方是否在改） | 交付物 |
|---|---|---|
| **我（单车车钩力控制）** | `src/train_dynamics/{coupler,braking,train}.py`（MT-2、缓释曲线、断面力）、`src/safety_layer.py`（enforce_coupler + ATP 规则顺序）、`src/multi_loco_controller.py`（AB 预测闸门/并发限制/充风门）、reward 车钩项（`coupler_over_term`） | 车钩力≤1000kN 落地率、peak/viol 指标、安全层诊断（Step 0/0.5 系列） |
| **队友（编队）** | `src/environments/train_fleet_env.py` 的编队上下文（`_dynamic_gap`/gap 目标/编队 obs）、formation vs No-C 消融、跨线免重辨识实验、列数扩展（3→5 列） | 列距/速度带指标、编队消融表、跨线主表行 |

**共享冲突热点（必须先约定单点 owner，避免两边同时改）**：`src/environments/train_env.py`（EBI 落地 + `safety_events` 计数）、`src/evaluation/evaluate_decompose.py`（主表出口）、`configs/experiments/*.yaml`、reward 组合处。**默认 owner = 改动发起方，改前在本文档加一行登记**（谁、哪个文件、动什么）。

**二、配合方式（4 条硬规矩）**

1. **物理同源铁律**：训练 / 评估 / 对比基线必须共用同一物理模型。**谁改物理，谁跑全量 `pytest tests/ -q` + 冒烟**（`--episodes 2` 且三输出目录全重定向），改动前后各留一份 `metadata.json`。
2. **接口先冻结再动手**：`obs_dim`、action 结构、**主表指标 JSON 键**（`reward / peak_coupler_kN / viol / safety_events / band_rate / ab_steps / mean_ed / gap_err_* / gap_min_m / mpc_*`）——键名要改，双方先同意 + Grep 全仓改齐，禁止单方改名。
3. **决策各自留痕、互不覆盖**：各自裁决 append 到本文档（加日期小节）；立论变更走 ADR；诊断细节入 `DIAGNOSTICS_2026-10.md`。日志 append-only，历史结论被推翻只标 `superseded`。
4. **术语统一**：指标中文标签按 `RESEARCH_POSITIONING.md` §1.7「指标术语对齐」执行（**禁自造词**，如"追尾步数"）；合并时发现旧词按该节改。

**三、怎么合并（顺序执行）**

1. **合并点 = 主训练冻结 commit**：两侧在同一 commit 上跑 `pytest tests/ -q` 全绿 + `check_agents_links.py` + `check_outputs_layout.py`，才启动 1400 ep × 5 seed 终局训练。**分叉期间各自跑的数不进主表**。
2. **主表单一出口**：由 `evaluate_decompose.py` 一处产出（我维护），队友只供数据不另开评估入口；表列顺序/单位口径由出口统一。
3. **合并前对齐 5 项**：① 同一物理与安全层（"一边改物理、一边做对比"= 无效实验）② 断面力口径（ADR-018）+ 1000 kN + 单位（m/s vs km/h）③ 时域三维度不混（ADR-017：rollout 窗 / 评估剖面 / 总训练量）④ seed 集与随机化初态设置 ⑤ ATP 触发次数、`assert rear_end_steps == 0` 守卫两侧一致。
4. **产物不打架**：`outputs/` 按类型分组 + 运行目录 `语义前缀_时间戳`，**三输出目录必须同时重定向**（checkpoint/results/figures），否则覆写历史（LRN-20261001-009）。
5. **合并后跑一次全量回归**：pytest + 冒烟 + 出一张主表核对列名与 §1.7 一致，再进论文。

**四、注意的地方（踩过的坑）**

- **别在对方跑训练时改共享文件**（`train_env.py`/YAML）——训练读的是启动时代码，中途改会静默不一致。
- **别把对方的口径当"待定"重提**：已定的以 ADR + `RESEARCH_POSITIONING` 为准；要推翻先拿证据。
- **别各自跑评估后直接拼表**：不同 commit / 不同物理的数值不可比（本项目已有"两侧物理同源"铁律）。
- **ATP 缺口 1（前车最坏假设）+ TTC/TET 是否在主训练前切口径，待拍板**（见 §1.7）——定了以后两侧都用新口径，别一半新一半旧。
